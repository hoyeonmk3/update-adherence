# Two-Stage Measurement of Update Adherence in Language Model Memory Agents

Benchmark scenarios, event records, frozen memory engine, and scoring scripts for the paper of the same title.

**Update Adherence (UA)** measures whether a revised requirement, and not the statement it replaced, governs the answer of a language model agent with external memory. It is scored at two stages with deterministic rules and no language-model judge: in the assembled context that the memory system hands to the answering model (context-level UA, categories Correct, Stale-Retained, Stale-Only, Lost) and in the generated answer (strict answer-level UA, categories NewOnly, Both, OldOnly, Neither). Every number in the paper can be recomputed from the files in this repository.

## Reproducing the paper from the released files

No model is needed for this step.

```bash
pip install -r requirements.txt
shasum -a 256 -c MANIFEST.sha256        # integrity of engine, scenarios, results, figure data
python analysis/make_tables.py           # writes analysis/tables.md and figures/data/*.csv
```

`analysis/tables.md` then contains Tables 5 to 9 of the paper, the context-by-answer cross-tabulations, the event breakdowns quoted in the Results, the retention summary with the paired bootstrap intervals, and the figure data.

## Re-running the experiments

The runners call a local Ollama server and reproduce the reported outputs only on the pinned stack below, because serving stacks do not guarantee identical generation across versions. Each runner checks the Ollama version and stops on a mismatch. Scoring is deterministic given the generated outputs, so measurements on other stacks are valid in their own right but will not match the released files byte for byte.

```bash
python runners/run_holdout_v4.py          # canonical run, Batch A
python runners/run_holdout_v5.py          # canonical run, Batch B
bash runners/chain_a.sh                   # behavior probe, SS repeat, threshold sweep, SS-noRetire, implicit variants, Phi-3, RAG variants
bash runners/run_prompt_ablation.sh       # three answer prompts on the same replay
bash runners/run_embedder_transfer.sh     # bge-small-en-v1.5 and gte-small, thresholds unchanged and mapped
bash runners/run_fn_canonical.sh          # EpSem-SS on the F/N scenarios with event logging
python runners/run_tsread_arm.py          # TS-Read
python runners/run_mem0_arm_v3.py --server-log /path/to/ollama_serve.log   # Mem0, 16,384-token window per library call
python runners/dp2_make_pairs.py && python runners/dp2_embed.py            # similarity pairs (results/dp2_pairs.json, dp2_sims.json)
```

Run every command from the repository root. The runners were rewritten from the archived execution tree to repository-relative paths; the `runner_sha256` fields inside the result files refer to the execution copies.

## Notes on the result files

- `results/canonical/`: Batch A baselines (Naive, RAG, EpSem, EpSem-F) are in `v4_holdout_20260601_023636.json`; EpSem-SS for Batch A was rerun with the final supersession module and is in `v4_holdout_20260602_215257.json`, which the paper uses. The earlier EpSem-SS entries of the 06-01 file predate that module and are not reported. Batch B is `v5_holdout_merged.json`, the Phi-3 run is `holdout_phi3_medium_20260610_210237.json`.
- `results/behavior_*.json`: one record per scenario with the assembled context, the generated answer, the exact-string context flags per update event, the supersession events, and the replay time. Suffixes: `_imp` implicit variants, `_phi3` second backbone, `_prompt_ablation` three answer prompts on one replay, `_fn` Forgetting and Noise Tolerance scenarios, `_rerun` the repeated EpSem-SS run, `_ragk20` and `_ragreform` the two RAG variants, `_U003_replay{1,2}` two further replays of one RAG scenario.
- `results/superseded/`: two earlier Mem0 runs made with the default 4,096-token window, under which every extraction prompt was truncated. They are kept as a record and are not used.
- Figure files themselves are not part of the repository; the values behind each figure are in `figures/data/`.
